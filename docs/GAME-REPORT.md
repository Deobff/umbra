## 3. 唯一一个可复算的正面结论

`keyedDigest` 的完整定义、伪代码与可执行验证程序：`qa/verify/KEYED-DIGEST.md` + `VerifyDigest.java`。

```
javac -cp "lib/*" -d qa/verify qa/verify/VerifyDigest.java
java  -cp "qa/verify;lib/*" VerifyDigest <seed-bound.jar> <classIndex>
# 0 = MATCH   1 = MISMATCH（真篡改样本）   2 = 输入不可用
```

三态自检（五例）全部通过，含真篡改（翻转 1 bit 后重新封装索引仍报 MISMATCH）。

```
digest = HMAC-SHA256(digestKey, label || payload || [classRoot])
label  = d:c:+二进制类名 / d:r:+逻辑名 / d:loader / d:serial
payload= 常量池还原后的 class 字节
classRoot 只对受门控的业务类追加 32 字节
```

已知限制：native/库绑定档的 root 只在 DLL 内，无法第三方复算（native 绑定的固有代价）。

## 4. java2c 的最终定位

成本型保护，不是不可读。证据：
- 符号保留（umbra_native_0..5、umbra_m0.constprop.0）；
- 常量可见（movabs 0x9f60... ; xor）；
- 含循环方法可还原语义并动态验证（a(n)=1+2+...+n，4/4）。

当前状态：experimental，默认关闭（native.enabled=false），详见 `docs/JAVA2C-STATUS.md`。
主路径 --preset maximum 是绿的（Verification: OK + 运行 OK）。

## 5. 十条不变量（从每次失分里提炼）

| # | 不变量 |
|---|---|
| I1 | 任何构建不得在关键保护缺失时静默降级 |
| I2 | 失败必须显式、可观测，不得静默跳过 |
| I3 | 归档内不得出现密钥材料 |
| I4 | 水印派生必须需要密钥 |
| I5 | exe 与 library 两条路径的保护强度必须对等 |
| I6 | 形状不算安全（不得以结构相似代替真实保护） |
| I7 | 交付前必须自攻一次 |
| I8 | 覆盖率/强度指标必须报告在最弱单元，容器级数字不得单独成立 |
| I9 | 任何防住了的结论必须附带可复算的验证程序 |
| I10 | 参与密钥派生的输入必须集中声明并可打印；附加信息不得在未登记的情况下进入派生链 |
| I11 | 任何对 loader 的锚定都必须发生在最后一个改写 loader 的 pass 之后 |
| I12 | 任何比对的两侧必须证明是同一个对象（比对前打印来源标识） |

> 完整版（每条含来源 / 违反检测点 / 反例数字）：[docs/SECURITY-INVARIANTS.md](SECURITY-INVARIANTS.md)，117 行。
> 其中 **I8–I12 共 5 条**是最后 10 轮里由真实失败逼出来的，不是早期经验的复述。

## 6. 核心教训（按价值排序）

1. 改了但没生效，是最高频的失败模式 —— 本场出现 6 次：旧 jar 验证新代码、跨构建比 sha、
   static const 被 -O2 折叠、renamer 对未注入的类无效、GetMethodID 传错变量、比对双方不是同一对象。
   改完之后先证明这行被执行了，再谈它对不对。

2. 校验器不能放在被校验的载体里 —— V27。loader 是明文、校验逻辑在 loader 内，一次 ASM patch 全部失效。

3. 好的度量应该让人不安 —— V20。coverage 100% 对比 coverage 100% classes, 67% methods 加 skipped 行。

4. 错误消息会误导排查方向 —— V15。root/key mismatch 让我们查了三十多轮根不一致，
   而根一直是对的，真正的差异是没人当成参数的 ZIP comment。

5. 判决必须一致 —— 我拒绝过红队技术上扎实的成果（V22 CP 层、V19 加固），
   理由都是同路径不重复计分或不符合事先定的判据。如果因为很努力就放行，每一分都会变得可疑。

## 8. 一句话总结

> 这场比赛没有让 Umbra 变成不可破的东西。

> 而其中至少两条（V27、V20）是我们在写报告时才发现自己错得很离谱的地方。

## 结尾：三个视角的一句话总结

### native 侧（原文，redteam/native 各自撰写）
> native 侧已修：V15（晚阶段重写丢 zip comment 致运行期 master 不同，修复后 `openIndex ok` / `RUN=0`）、
> V27（loader 类锚定，patch 后自校验拒绝）、V28（bridge 槽锚定，探测调用与真实比对已用独立 verdict 区分）；
> 受同进程模型上限、不再作为待办：V14（按次数打断合法路径已撤）、V23（`gateTick` 无法区分同进程合法调用者与攻击者）。

### Lead 侧（不在 native 职责范围内的两条）
> V20（覆盖率类级口径掩盖被跳过的方法）与 V18（构建期 `%TEMP%` 残留翻译源码）由 Lead 修复，
> 均附可复跑验收（方法级覆盖行 / `%TEMP%` 计数为 0）。

### 这场比赛真正的结论
> **这套系统的所有防线都是「防离线」的，不是「防进程内」的。**
> 能挡住的人：只拿到产物、不运行它的分析者。
> 挡不住的人：能在目标 JVM 内执行一段代码的攻击者。
>
> 这不是缺陷，是**进程内密钥分发**这件事的物理上限。
> 一份诚实的报告必须把这句话写在最前面，而不是藏在附录里。
